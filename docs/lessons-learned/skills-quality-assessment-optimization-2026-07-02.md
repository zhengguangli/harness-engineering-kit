## 二、关键经验

### 经验1：同步方向很重要

**问题**: 之前执行了 `rsync -av --delete skills/ ~/.agents/skills/`，把项目同步到了用户目录。改进时只在用户目录修改，导致项目目录未更新。

**教训**: 
- 同步前先确认方向：是从项目→用户，还是用户→项目
- 改进工作应在项目目录进行，完成后同步到用户目录
- 使用 `git status` 验证变更是否在正确的位置

**最佳实践**:
```bash
# 改进工作流程
1. 在项目目录进行修改
2. git add + git commit
3. rsync -av --delete skills/ ~/.agents/skills/
4. 重新软连接 ~/.claude/skills
```

### 经验2：边界情况可以通用化

**问题**: 13个skills中有7个边界情况重复出现（项目规模极小、遗留项目改造、多团队协作等），导致内容冗余。

**教训**:
- 识别跨skills的通用模式
- 创建通用参考文档，各skill引用
- 只保留skill特定的边界情况

**成果**:
- 创建 `docs/references/common-edge-cases.md`
- 边界情况章节内容减少40%
- 维护成本降低，一致性提升

### 经验3：端到端示例提高可执行性

**问题**: 虽然skills内容详实，但缺少从开始到结束的完整示例，用户难以直接使用。

**教训**:
- 为关键skill提供端到端完整示例
- 示例应包含：输入→处理→输出→错误处理
- 示例应基于真实场景，可以直接使用

**成果**:
- 新增3个端到端示例（architecture-boundaries/exec-plans/repo-map）
- 提高了skills的可执行性

### 经验4：references文件遵循上下文预算

**问题**: skills正文过长会超出上下文窗口，影响使用效果。

**教训**:
- 将详细内容放在references/子文件
- SKILL.md只保留核心内容和引用
- 遵循"渐进式披露"原则

**成果**:
- 扩展了25个reference文件
- SKILL.md更精简，references更详细
- 符合上下文预算纪律

### 经验5：交接点说明提高工作流顺畅度

**问题**: skills之间的交接点说明不够详细，影响工作流的顺畅度。

**教训**:
- 明确前置条件
- 清晰输入输出
- 完善错误处理
- 有效的验证方法

**成果**:
- 加强了orchestration/verification-loop/commit-gate的交接点说明
- 提高了工作流的顺畅度

### 经验6：自动化检查提高效率

**问题**: 手动评估效率低，且容易遗漏。

**教训**:
- 优化自动化检查脚本
- 支持批量评估
- 结构化输出（JSON）

**成果**:
- 优化了skill-quality-assessor和repo-map的自动化检查脚本
- 提高了评估效率和准确性

## 四、可复用的工作流程

### 质量评估流程
```
1. 使用 harness-skill-quality-assessor 进行批量评估
2. 生成评估报告，识别改进方向
3. 按优先级执行改进建议
4. 验证改进效果
```

### 改进执行流程
```
1. 精简冗余内容（边界情况、重复说明）
2. 增加端到端示例
3. 扩展references文件
4. 加强交接点说明
5. 补充技术栈示例
6. 优化自动化脚本
```

### 同步流程
```
1. 在项目目录进行修改
2. git add + git commit + git push
3. rsync -av --delete skills/ ~/.agents/skills/
4. rm -rf ~/.claude/skills && ln -s ~/.agents/skills ~/.claude/skills
```

## 五、注意事项

1. **同步方向**: 确保从项目→用户，而不是反向
2. **git验证**: 改进后用 `git status` 验证变更位置
3. **通用化**: 识别跨skills的通用模式，创建通用文档
4. **上下文预算**: 详细内容放references，核心内容留SKILL.md
5. **交接点**: 加强skills之间的交接点说明
6. **自动化**: 优先使用自动化脚本，提高效率
