# Routing Decision Tree Reference

This file is an independently loadable reference for the `harness-orchestration` skill — it extracts the decision tree and transition points from SKILL.md into structured knowledge that agents can consult on demand. Detailed workflow steps are in SKILL.md; this file only retains extended content that does not fit in SKILL.md.

## Three-Level Routing

Faced with a task, use these 3 levels of judgment to route quickly:

```
What does the user want?
├── Initialize / New project → Workflow 1
├── Write code / Modify code → Workflow 2
│   ├── Task complexity?
│   │   ├── Simple (can be completed in one session) → skip exec-plans, directly verification-loop + commit-gate
│   │   └── Complex (cross-session) → exec-plans → verification-loop → commit-gate
│   └── Involves UI/performance?
│       └── Yes → trigger observability-and-browser within verification-loop
├── Fix quality / Clean up → Workflow 3
│   ├── Pure taste drift → golden-principles → verification-loop → commit-gate
│   └── Structural violations → golden-principles + architecture-boundaries → verification-loop → commit-gate
└── Add capability to harness → Workflow 4
    └── Finally, add one row each in the target project's architecture document domain table and quality score table (carried by the skeleton structure generated by `bootstrap`)
```

## Transition Point Table

The following artifacts have clear "upstream output to downstream consumer" relationships between skills:

| Upstream Skill | Artifact | Downstream Consumer |
|---|---|---|
| `project-intake` | Structured project card | `bootstrap` (uses card info to generate skeleton) |
| `exec-plans` | exec-plan file | `verification-loop` (executes steps from plan and writes back progress) |
| `architecture-boundaries` | lint rules / structured tests | `verification-loop` (as self-check items), `commit-gate` (as gate check) |
| `observability-and-browser` | Screenshots/screen recordings/metric query results | `verification-loop` (as fix evidence), `commit-gate` (as completion proof) |
| `golden-principles` | Fix queue (list of deviation patterns) | `verification-loop` (fix one by one) |
| `repo-map` | CLAUDE.md + documentation validation report | `bootstrap` (verify skeleton completeness), `authoring` (confirm new skill has been registered) |

## Common Omissions

These 12 skills are used on demand — you do not need to go through all of them every time:

- Small projects do not need `architecture-boundaries` (no multi-layer architecture to guard).
- Pure documentation changes do not need `verification-loop` and `observability-and-browser`.
- Projects that already have a well-established harness structure do not need to re-run Workflow 1.
- `authoring` is only used when extending the harness system itself; it is not needed for daily development.
