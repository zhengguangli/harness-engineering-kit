# 通用边界情况参考文档

## 概述

本文档汇总了 Harness 体系中各 skill 共享的通用边界情况处理方案。各 skill 在处理这些边界情况时，应引用本文档而非重复定义。

## 通用边界情况

### 1. 项目规模极小

**场景**：项目只有几个文件，模块间无明显分层需求

**处理原则**：
- 简化初始化，只创建必要的文件
- 跳过重量级 skill（如 architecture-boundaries）
- 使用简单的目录结构，不需要复杂架构约束

**判断标准**：
- 文件数量 < 10
- 代码行数 < 1000
- 开发团队 < 3人

### 2. 遗留项目改造

**场景**：遗留项目存在大量架构违规或代码异味，需要逐步改造

**处理原则**：
- 采用渐进式改造策略，优先修复严重违规
- 不破坏现有结构，增量更新
- 保留现有有价值的内容

**改造步骤**：
1. 识别所有违规/异味
2. 按严重程度分类（CRITICAL/HIGH/MEDIUM/LOW）
3. 优先修复CRITICAL和HIGH级别问题
4. 建立新规则，防止新增违规
5. 逐步清理MEDIUM和LOW级别问题

### 3. 多团队协作

**场景**：多个团队协作开发，需要统一规范

**处理原则**：
- 建立统一的规范，各团队在规范内自由实现
- 定期审计规范执行情况
- 建立规范 review 流程

**协作方案**：
1. 建立统一的规范模板
2. 为每个团队提供定制化配置
3. 定期审计规范执行情况
4. 建立规范 review 流程

### 4. 基础设施缺失

**场景**：项目缺少必要的测试/构建/lint 配置

**处理原则**：
- 先补齐基础设施，再启动相关流程
- 报告能力缺口，不退回读代码猜测
- 使用备用验证方式（如静态分析）

**补全步骤**：
1. 识别缺失的基础设施
2. 报告能力缺口
3. 建议先运行 harness-bootstrap
4. 补齐配置后再启动相关流程

### 5. 目标澄清

**场景**：用户描述的需求模糊，无法确定具体范围

**处理原则**：
- 先澄清用户目标，再进行路由
- 用"待澄清问题"列出，不替用户做决定
- 澄清后再创建执行计划

**澄清方法**：
1. 列出待澄清问题
2. 等待用户澄清
3. 澄清后再执行

### 6. 跨平台同步

**场景**：同时为 Codex 和 OpenAI agents 创建重复的入口文件

**处理原则**：
- 只创建自己平台的入口文件
- 确保两个版本逐字一致（仅允许工具名差异）
- 定期检查同步状态

**同步检查**：
1. 对比 .md 和 .openai.yaml 的 system_prompt
2. 检查是否有差异
3. 如果有差异，修正为一致
4. 仅允许工具名差异（Bash ↔ exec_command 等）

## 使用指南

各 skill 在处理边界情况时：
1. 如果边界情况属于上述通用类型，直接引用本文档对应章节
2. 如果边界情况是 skill 特有的，在 skill 的 SKILL.md 中保留并详细说明
3. 保持 skill 特有边界情况的格式：场景 → 处理原则（1-2行）
