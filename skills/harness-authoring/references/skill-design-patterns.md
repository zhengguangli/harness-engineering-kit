# Skill 设计模式参考

## 设计模式总览

| 模式 | 适用场景 | 复杂度 |
|---|---|---|
| 知识注入型 | 主对话需要持续参考某领域知识 | 低 |
| 流程引导型 | 复杂多步骤任务需要结构化流程 | 中 |
| 检查清单型 | 验证/审计场景需要逐项检查 | 低 |
| 工具编排型 | 需要协调多个工具/子agent | 高 |
| 渐进披露型 | 信息量大需要分层加载 | 高 |

## 模式一：知识注入型

最简单的 skill 形态——将领域知识注入当前上下文供主对话参考。

**结构模板**：

```yaml
---
name: domain-knowledge
description: 为 XXX 场景提供领域知识参考。
context: fork
compatibility: claude-code
---
# Domain Knowledge

## 核心概念
- 概念A：定义与边界
- 概念B：定义与边界

## 决策规则
- 当遇到 X 时，选择 Y
- 当遇到 Z 时，选择 W

## 常见误区
- 误区1：...（正确做法：...）
- 误区2：...（正确做法：...）
```

**设计要点**：
- 正文控制在 200 行以内（这类 skill 通常很精简）
- 核心概念 ≤ 10 个，超出则拆分到 references/
- 决策规则用"当...时，选择..."句式，消除歧义

**反模式**：
- ❌ 把整本教科书塞进 skill——应拆分到 references/ 按需加载
- ❌ 概念定义模糊——"X 是一种很好的实践"不如"X 指的是：1/2/3"

## 模式二：流程引导型

定义复杂多步骤任务的执行流程，主对话按步骤推进。

**结构模板**：

```yaml
---
name: workflow-guide
description: 引导 XXX 流程的执行——从 A 到 B 到 C。
context: fork
compatibility: claude-code
---
# Workflow Guide

## 核心原则
- 原则1：...
- 原则2：...

## 执行流程

### Phase 1: 准备
1. 步骤1（检查 X）
2. 步骤2（准备 Y）

### Phase 2: 执行
3. 步骤3（执行 A）
4. 步骤4（验证 B）

### Phase 3: 收尾
5. 步骤5（记录 C）

## 边界情况
- 情况1 → 处理方式
- 情况2 → 处理方式
```

**设计要点**：
- Phase 数量 ≤ 5，每个 Phase 内步骤 ≤ 5
- 每个步骤必须是可执行的（不是"考虑X"而是"检查X是否存在"）
- 边界情况用"情况→处理"映射，不要写长段落

**反模式**：
- ❌ 步骤描述模糊——"做好准备工作"不如"确认以下3项已就绪：..."
- ❌ 缺少终止条件——每个 Phase 应有明确的"完成标准"

## 模式三：检查清单型

验证/审计场景的逐项检查结构。

**结构模板**：

```yaml
---
name: quality-checklist
description: 检查 XXX 是否符合质量标准。
context: fork
compatibility: claude-code
---
# Quality Checklist

## 检查项

### 必检项（全部通过才算合格）
- [ ] 检查项1：标准描述 + 判定方法
- [ ] 检查项2：标准描述 + 判定方法

### 推荐项（建议通过）
- [ ] 检查项3：标准描述 + 判定方法

## 判定规则
- 全部必检项通过 → ✅ 合格
- 任一必检项未通过 → ❌ 不合格，列出未通过项
- 推荐项未通过 → ⚠️ 警告，不阻塞

## 输出格式
| 检查项 | 结果 | 证据 |
|---|---|---|
| 检查项1 | ✅/❌ | 具体证据 |
```

**设计要点**：
- 必检项 ≤ 10 项，超出则分组
- 每项必须有明确的判定方法（不是"看起来对"）
- 输出格式固定，便于自动化解析

## 模式四：工具编排型

协调多个工具或子 agent 完成复杂任务。

**结构模板**：

```yaml
---
name: tool-orchestrator
description: 编排 XXX 工具链完成 YYY 任务。
context: fork
compatibility: claude-code
---
# Tool Orchestrator

## 工具清单
| 工具 | 用途 | 权限 |
|---|---|---|
| tool1 | 用途1 | read |
| tool2 | 用途2 | read, write |

## 编排流程
1. 调用 tool1（输入：A，输出：B）
2. 基于 B 判断路由
3. 路由1 → 调用 tool2
4. 路由2 → 调用 tool3

## 错误处理
- tool1 失败 → 重试1次，仍失败则终止
- tool2 超时 → 切换到备用工具
```

**设计要点**：
- 工具清单包含权限声明（呼应最小权限原则）
- 编排流程用数据流描述（输入→处理→输出）
- 每个工具调用必须有错误处理路径

## 模式五：渐进披露型

信息量大的知识体系分层组织。

**结构模板**：

```yaml
---
name: progressive-knowledge
description: XXX 领域知识——按需深入。
context: fork
compatibility: claude-code
---
# Progressive Knowledge

## 核心概念（始终加载）
- 概念1：一句话定义
- 概念2：一句话定义

## 深入指南（按需加载）
- 详细内容 → 参考 `references/deep-dive-1.md`
- 详细内容 → 参考 `references/deep-dive-2.md`

## 快速参考（高频查阅）
| 场景 | 做法 |
|---|---|
| 场景A | 做法1 |
| 场景B | 做法2 |
```

**设计要点**：
- 核心概念控制在 5 个以内（始终加载的部分）
- 深入指南用文件引用，正文只写"什么情况下读哪个文件"
- 快速参考表覆盖最高频的 80% 场景

## 选择模式的决策树

```
需要注入知识到主对话？
├── 知识量少（< 200行）→ 知识注入型
├── 知识量大 → 渐进披露型
└── 需要执行流程？
    ├── 线性流程 → 流程引导型
    ├── 需要判断路由 → 工具编排型
    └── 需要逐项验证 → 检查清单型
```

## 混合模式

实践中经常混合使用：

| 混合方式 | 示例 |
|---|---|
| 知识注入 + 检查清单 | 领域知识 + 质量检查标准 |
| 流程引导 + 工具编排 | 多步骤流程中嵌入工具调用 |
| 渐进披露 + 流程引导 | 核心流程 + 按需深入的参考资料 |

**混合原则**：以一种模式为主，其他模式为辅。不要在一个 skill 里同时使用 3 种以上模式，否则结构会混乱。
